# Async plans and recovery

Treat plan paths as estimates. For an accepted plan, dispatch every entry in `ready_milestones` in the same turn, using one background `purser:dispatcher` Agent call per pass. Submit all calls before waiting for any result. Include shared generated files and validation inputs when judging disjointness. For worktree jobs, dispatch overlapping paths immediately: Purser queues hot-path conflicts as `QUEUED` and auto-starts them on lease release; otherwise jobs run in parallel worktrees and resolve overlap at apply. Wait only for a logical dependency, such as a milestone needing the previous milestone's applied result; a reply on a conflicting scope is still denied. Main Claude calls `codex_result` once for each job, reviews each complete bundle on its own delta, and applies the reviewed revision directly. Otherwise run disjoint work sequentially.

Use the SessionStart duration hint for `eta` when present. The dispatcher starts every job with `codex_start`; for continuation pass `mode=reply`, `threadId`, the same ORCH `task`, and no `cwd`. Main Claude uses `codex_cancel` only at user request. Never cancel a job that was applied; cancelling discards it.

After `codex_apply` reports a replay conflict, main Claude resolves and commits the files by hand, then calls `codex_apply` with the same `jobId` and `resolved: true`. This records the hand-applied job as accepted and releases its scope lease. When main Claude applies a job by hand for any other reason (stale apply, failed finalization), it calls `codex_apply` with that `jobId` after committing: the files already match the worktree, so the job is recorded as applied and its lease is released.

For legacy in-flight dispatchers that already published a result or acceptance receipt, main Claude collects the published bundle with one `codex_result` call, reviews it, and applies directly with `codex_apply(jobId, revision)`. Do not rewrite job records or wait for the old dispatcher to apply. If sessions differ, use the same-project `adopt=true` result path; it requires explicit adoption and a durable result. Run the exact validation waiter returned by apply with PowerShell on Windows or Bash on macOS/Linux. Preserve its returned quoting and platform behavior, including hidden child launches, process ownership, long-path handling, and antivirus file-lock retries. On permission denial, stop and report the denied tool and command. On timeout, empty exit 255, or `STILL_WAITING`, repeat the same returned command for the same job; an empty exit is an observation failure, so reconcile the durable record rather than restarting the job. Confirm terminal status and required command coverage before commit; a zero waiter exit by itself is insufficient.

When an accepted part of an approved multi-part task finishes, start the next part in the same turn without asking. Stop only for approval-gated actions, real decisions, failed review, or residual risk the user must weigh. Quota is not a reason to stop unless 5h or 7d remaining is at most 10%; then warn before the task and let the user choose.

With several jobs, keep a list of finished results the user has not yet decided on. Present them one at a time in finish order, and do not move to the next one or to new work until the user has answered on the current one.
